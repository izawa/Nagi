# M1 コアと木漏れ日の計画

版: 0.1(2026-11-18)/状態: 作者の判断を反映。段階 1 の前

M1 では、凪のコア(NagiKit、NagiCore)と木漏れ日を作り、署名と公証を通した dmg(v0.1)にする(SPEC 7 章)。この文書は、作る順序、確かめ方、作者に見てもらう区切りを決める。

計画は Claude と Codex がそれぞれ独立に作り、突き合わせて 1 つにした。どちらの案から何を採ったかは 10 章に書く。

## 1. 前提

### 1.1 開発機

M0 と同じ(M0-PLAN 1.1)。Mac mini(M4 Pro)、macOS 27.2.1、Studio Display(5K、60 Hz)1 台。内蔵ディスプレイと 120 Hz の画面はない。

### 1.2 M1 で作るもの

SPEC 7 章の M1 の項目、つまり NagiKit、NagiCore、凪の状態機械、オーバーレイ、合成、共有環境、木漏れ日、`nagi-render` とギャラリー、メニューバー、設定、ログイン時の起動、署名と公証を通した dmg。

完了の条件は 2 つある。

- SPEC 4.1 の受け入れ基準 7 項目を、作者が目で見て通す(確かめ方は 5 章の表)
- 活動中の CPU と GPU の使用がほぼゼロ。合格の線は 7.3 に案を置き、作者が決める

### 1.3 M1 で作らないもの

画面の取り込み(3.9)、権限の画面(2.5 の「権限」)、ランダムモード(2.3)は M2、ウィンドウ情報(3.10)は M3 で作る。ただし、M2 の完了の条件「エフェクトを足すときにコアに手を入れない」を守れるよう、M1 のうちに次の 2 つを試験用のエフェクトで通しておく。

- `.glass` の層と、2 つの層を同時に重ねること
- `.backdrop` を求めたエフェクトに、合成済みの背景テクスチャを渡すこと(取り込みの代わりに、試験用の画像を渡す)

### 1.4 API の確認

SPEC 10 章の 2 に従い、使う前に SDK のヘッダーか公式ドキュメントで確かめる。M1 の最初の段階で確かめるのは次の 3 つ。

- `CAMetalDisplayLink` のシグネチャと、動かすラン ループのモード
- `swift build` で作った .app で、文字列のリソース(多言語)が読めるか。.app をアーカイブで作らないので(DECISIONS D12)、確かめておく
- スクリプトで組み立て、Sandbox を有効にした .app で、SwiftUI の `MenuBarExtra` と設定の画面が動くか

## 2. 置き場所と作り

SPEC 3.2 の構成【決定】に従う。依存の向きは Swift パッケージの定義で強制する。

```text
App/                    アプリ本体。エフェクトの登録の一覧もここに置く
Packages/NagiKit/       エフェクト API(プロトコルと値型だけ)
Packages/NagiCore/      エンジン
Packages/Effects/KomorebiEffect/
Tools/nagi-render/      オフスクリーン描画のコマンド。エフェクトの登録の一覧は App と共有する
scripts/                build-app.sh、release.sh、measure-load.sh
Fixtures/               nagi-render と試験で使う背景の画像とウィンドウの配置
```

.app は `swift build -c release` の成果物から組み立て、リソースのバンドルを `Contents/Resources` に置いて内側から順に署名する(DECISIONS D12)。M0 の `build-spikes.sh` を元にする。ただし M0 は署名のタイムスタンプを付けていない(`--timestamp=none`)ので、リリースの署名ではタイムスタンプを付け、公証の前に確かめる。M0 の Harness と Fixture は `Spikes/` に残し、測定にだけ使う。

## 4. NagiKit と NagiCore

### 4.1 エフェクト API

SPEC 3.4 の例示を元に、段階 1 で最初の版を作り、段階 2 の試験(4.3)が通るまでは固めない。

- `EffectDescriptor`: id、表示名と説明、`layer`、`capabilities`(`.backdrop`・`.windows`・`.extendedRange`)、パラメータの宣言、`weatherHint`
- `FrameState`: 値型。単調な時刻と差分、壁時計の日時、凪の局面、`presence`、`depth`、外観、品質、アクセシビリティの調整、パラメータの現在値、乱数の種、共有環境。`.windows` を求めたときだけウィンドウの一覧(M3)
- `DisplayView`: ディスプレイの ID、ピクセル寸法、倍率、デスクトップの中の位置、物理寸法(mm)、EDR の余裕(今の値と最大)、`.backdrop` を求めたときだけ背景テクスチャ
- 同じ種と時刻なら同じ絵になる。`nagi-render` と基準画像の試験はこれに頼る

### 4.2 Metal の持ち主

- コアが持つもの: デバイス、コマンドキュー、コマンドバッファ、エフェクトごとの出力のテクスチャ、合成、表示
- エフェクトが持つもの: 自分のシェーダーのライブラリ(自分の `Bundle.module` から読む)、パイプライン、作業用のバッファとテクスチャ
- `EffectEncoder` は、自分の出力のテクスチャへの描画のパスと、作業用の計算のパスを、クロージャの範囲だけ貸す。コマンドバッファの確定と表示はコアだけが行う
- 出力は乗算済み RGBA、`rgba16Float`、拡張リニアの Display P3(SPEC 3.5)

### 4.3 描画のスレッドと、必ず消えること

`T_leave`(0.8 秒)はコアが強制する安全装置である(SPEC 1.1、3.3)。段階 2 で次のように決めた(記録は `docs/M1-LOG.md`)。

- 描画はメインスレッドで回す(`CAMetalDisplayLink` をメインのラン ループの `.common` に付ける)。メニューを開いているあいだもフレームは来る
- 無入力の秒数は IOHIDSystem の `HIDIdleTime` で読む(区切り A で `CGEventSource` から切り替えた。DECISIONS D14)
- 入力の見分け方: 無入力の秒数の下がりか、無入力の秒数から逆算した「最後の入力の時刻」が、凪が出たとき(または「今すぐ見る」を選んだとき)より 0.1 秒以上あとになったこと。後者で、入力が続いて値が下限に張り付く場合と、「今すぐ見る」の直後のキー 1 回も拾える
- 限界: 「今すぐ見る」を選んだクリックから 0.1 秒以内のキー 1 回は、クリックと見分けられない(無入力の秒数は最後の入力からの秒数しか返さない)。そのあと何か入力すれば凪は引く
- メインスレッドが止まると、入力に気づくことも、ウィンドウを画面から外すこともできない。そこで見張り(`WithdrawalGuard`)を別のスレッドに置く。凪が出ているあいだだけ 8 ms ごとに無入力の秒数を読み、入力を見てから 0.5 秒たってもまだ出ていれば、Core Animation でレイヤーを隠す(0.8 秒から、スクロールが `HIDIdleTime` に表れるまでの約 0.2 秒と、隠してから画面に表れるまでを引いた)(メインスレッドは要らない)。メインスレッドが戻ったら、ウィンドウを外して後片付けをする
- 見張りとは別に、メインスレッドの番犬も置く。退場の期限が来たら、フレームが届いていなくてもウィンドウを外す
- 番犬か見張りが外したあとは、状態機械がいったん活動中に戻るまで、凪を出さない
- 最後の合成のパスで、色とアルファの両方に `presence` を掛ける。`presence` 0 では完全に透明にする
- 模擬の入力とメインスレッドを 1.5 秒止める試験で、止まっている最中の入力でも 0.51 秒で隠れ、取り込みでも 0.55 秒以内に消えた
- NagiKit のエフェクトは、メインスレッドから順に呼ばれる。並行性の注釈は付けない(付けなくても、エフェクトは 1 つのスレッドだけから呼ばれる)

### 4.4 NagiCore の中

- 状態機械: 純粋な値型。偽の時計と偽の無入力の秒数で単体試験する。活動中、入場中、凪、退場中
- 無入力の監視、抑制の監視: OS からの入力(無入力の秒数、電源アサーション、画面の状態の通知、低電力モード、アクセシビリティの設定)を状態機械へ渡す
- オーバーレイの管理: ディスプレイごとのウィンドウ。位置・大きさ・倍率が変わったときだけ作り直す
- 描画: エフェクトの生涯、層の順の合成、`presence` の適用。実際の画面と `nagi-render` で同じものを使う
- 共有環境(SPEC 3.6): 日時と緯度経度からの太陽の高度・方位・色温度、月の位置と月齢、雲量(エフェクトの `weatherHint` を混ぜる)、風。場所の既定はタイムゾーンの代表都市で、設定で緯度経度を指定できる。位置情報サービスは使わない。太陽と月は既知の値と比べる単体試験を置く

### 4.5 今すぐ見ると一時停止

SPEC 2.4 の「今すぐ見る」は 30 秒間、凪を強制する。扱いは次のとおり(2026-11-18 に作者が決定)。

- 選んだあと、手が 0.5 秒止まった時点で入場する(`T_onset` は待たない。区切り A のあとに作者が決定、DECISIONS D15)。10 秒たっても手が止まらなければ取りやめる。動画と会議の抑制は無視する。画面のロック、スクリーンセーバー、ディスプレイのスリープ、一時停止のあいだは出さない
- 入力があれば、ふだんの凪と同じく `T_leave` 以内に引く(安全装置は破らない)
- 一時停止は「1 時間」「今日いっぱい」「再開するまで」の 3 つ。期限は壁時計で持ち、スリープをまたいでも正しく切れることを試験する

## 5. 木漏れ日の作り方

段階 3 と 4 で、次の順に作る。どれも `nagi-render` の画像で確かめてから進む。

1. 樹冠の層を 1 つ作り、太陽の方向へ投影し、円盤でぼかす
2. 層を 3〜4 つ(1.5 m、4 m、10 m など)にする。光線に垂直な円の直径は `0.0093 × h / sin θ`。地面では太陽の方位に沿って `1 / sin θ` 倍に伸び、`0.0093 × h / sin² θ` の楕円になる。画面の物理寸法で実寸にする
3. 枝の階層と葉のインスタンスを、種から作る。葉は少し色のついた光を通す
4. 全層の透過率を掛け合わせ、直射光と空の光を足す
5. 出力: ライトの外観は影(α 0.08 までの黒、DECISIONS D3)で、影にわずかに緑から青の色かぶりを入れる。夕方は日なたの色を暖かくする。ダークの外観は α を持った明るい色(D1)。EDR は対応ディスプレイで、日なたを白より明るくする
6. 風: 幹(0.1〜0.3 Hz)、枝(0.5〜1 Hz)、葉(2〜5 Hz)の 3 階層。共有環境の風のノイズ場で動かし、突風の前線が樹冠を渡る。周期を持たない
7. 雲: 雲がかかると、暗くするのではなく、木漏れ日のコントラストを下げて空の光に寄せる
8. 深まり: 浅いうちは高い梢の円だけ。20 秒ほどから低い枝の葉影と風の表情を足す
9. 入場と退場: 雲が晴れる・かかるように、コントラストを上げ下げする。コアの `presence` はその上から掛かる
10. 夜: 月明かり(ごく弱く、青い)。設定でオフにできる。既定は作者が区切り C で決める

10 m の梢の円は、太陽が真上のとき直径 9 cm ほどで、5K の画面では約 800 px になる。太陽が低いと楕円の長い軸は `1 / sin² θ` で伸び、高度 30° では約 3,200 px になる。そこで、大きなぼかしは低い解像度で行い(SPEC 3.11)、太陽が地平線に近いときの扱い(ぼかしの上限か、出さないか)を決める。フレームの時間は段階 3 の区切り B の前に測り、動きを足した段階 4 の終わりにもう一度測る。120 Hz の上限と、熱状態で品質を下げる動きも段階 4 で確かめる。

| 4.1 の受け入れ基準 | 確かめ方 |
|---|---|
| 高い隙間は円に、低い葉は葉の形に見える | 正午のピンホールと葉の画像、浅い・深いの実寸の画像。夕方の伸びも見る(区切り B) |
| 10 分眺めても繰り返しに気づかない | 実際の画面で 10 分通して見る。全体のコンタクトシートでも、戻りや繰り返しを探す(区切り C) |
| 突風が渡るのが見える | 種を固定して前線を 1 本だけ通す連番画像。枝が通る順に揺れること(区切り C) |
| 雲で木漏れ日が溶け、また戻る | 晴れ → 曇り → 晴れの連番画像。全体が暗くならないこと(区切り C) |

## 7. 試験と道具

### 7.1 合成の式をそろえる

`nagi-render` で背景の画像の上に重ねるときは、M0 で測った式(SPEC 3.5、符号化した値での合成)を使う。線形の値で重ねると、D1 と D3 の強さを、実際とは違う絵で決めてしまう。式は NagiCore に 1 か所だけ置き、M2 の背景テクスチャの合成でも同じものを使う。

段階 3 で、`nagi-render` の予想と、実際のオーバーレイを取り込んだ値を比べる。既定の `.none` は取り込みに写らない(S6)ので、比べるときは試験用の設定で `.readOnly` にし、M0 の画面収録を許可した Harness を元にした道具で、動いている Nagi のオーバーレイを読む。1 を超える合成は M0 で確かめていないので、EDR は区切り B で実際の画面を見て決める。

### 7.2 入力から消えるまでの測り方

新しい権限は求めない。前面に置いた Fixture が自分の受けた入力の時刻(`NSEvent.timestamp`)を記録し、Nagi の記録と突き合わせる。2 つの時刻が同じ時計(`systemUptime`)か、最初に確かめる。

- Nagi は、入力に気づいた時刻、退場を始めた時刻、ウィンドウを画面から外した時刻、凪に入った時刻を記録する
- 画面から実際に消えた時刻は、`.readOnly` にした試験用の設定で、画面収録を許可した道具が取り込んで確かめる
- メニューを開いているあいだの入力は Fixture に届かないので、そのときは Nagi の記録とメニューの操作の時刻で測る
- `T_onset` の実際の時間も同じ仕組みで測る。「1 フレーム以内」(D7)と「0.8 秒以内」(`T_leave`)は別々に報告する

### 7.3 作業中の負荷

5K・60 Hz の Studio Display で、Nagi を終了した状態と常駐させた状態を、同じ入力を続けながら交互に測る(M0 の `measure-load.sh` を元にする)。合格の線の案は次のとおりで、作者が決める。

- 構造の条件: 退場の期限のあと、オーバーレイのウィンドウが画面になく、表示の同期が止まり、GPU への描画の送り出しがない。活動中は、次に `T_onset` に達しうる時刻まで寝ていて、常時ポーリングしない(SPEC 3.8)
- 数値: Nagi の CPU、WindowServer の CPU、GPU の利用率を、終了したときと比べて報告する。どこまでの差を「ほぼゼロ」とみなすかは、作者が数値を見て決める

凪の間は、フレームの間隔、落ちたフレーム、GPU の時間、メモリを測る。1 秒に 3 回を超える点滅がないか(SPEC 2.2、`Tools/flicker.py`)も、本文、平らな面、葉の縁の上で測る。

### 7.4 nagi-render とギャラリー

```sh
nagi-render komorebi --at 2026-06-21T12:00:00+09:00 --depth 35 --presence 1 \
  --appearance light --seed 42 --background Fixtures/reading-light.png \
  --size 1600x1000 --physical-mm 400x250 --output noon.png
```

動きは `--fps 60 --frames 600`(10 秒分)で連番画像にする。10 分の通しのコンタクトシートは、`--every 5s` のように間隔を空けて 10 分全体から抜き出す。ウィンドウの配置は `--windows <JSON>` で渡せるようにする(SPEC 3.12。木漏れ日は使わないが、M3 で使う)。基準画像は、作者が通した少数(浅い・深い、ライト・ダーク、正午・低い太陽)だけを持ち、開発機で許容差つきで比べる。ギャラリーは同じ描画を使い、`Fixtures/` の見本の背景の上で、`depth`、時刻、局面、外観をスライダーで動かす。

## 10. 2 つの案の突き合わせ

骨組みは両案で同じだった。描画と確認の道具を先に作り、凪の出入り、木漏れ日、アプリ、リリースの順に進める。

| 採った点 | 案 | 理由 |
|---|---|---|
| 作者の区切りを 4 つ(A〜D)と最後の確認に置く | Codex | 作者の時間を前もって伝えられる |
| 入力から消えるまでを、物理的な入力から測る | Codex | `T_leave` は利用者が感じる時間なので |
| 期限の番犬 | Codex | 描画が届かなくても必ず消すため |
| 木漏れ日を 10 の小さな段に分け、毎回画像で確かめる | Claude | 美しさの判断を細かく区切れる |
| 太陽の位置を単体試験する | Claude | 時刻の誤りは画像では気づきにくい |
| 描画のスレッドを試験で決める | 両案の違いから | メインスレッド案は簡単、専用スレッド案は止まりに強い。どちらが要るかは測れば分かる |
| `nagi-render` の合成を M0 の式にそろえる | アドバイザー | 違う絵で強さを決めないため |
| M2 のための試験用エフェクト(`.glass`、背景テクスチャ) | アドバイザー | M2 の完了の条件をコアの変更なしで満たすため |
| CPU 0.2% の合格の線 | 採らなかった(Codex) | 作者が決めていない数値なので、構造の条件を案にし、数値は報告にとどめる |
