# M0 技術検証の計画

版: 0.2(2026-11-18)/状態: 作者の判断を反映。実行中

M0 では、SPEC.md の【要検証】を実験で確かめる。この文書は、その実験の中身、順序、作者に頼む操作を決める。結果は `docs/SPIKES.md` に書き、SPEC.md を直す。

計画は Claude と Codex がそれぞれ独立に作り、突き合わせて 1 つにした。どちらの案から何を採ったかは 6 章に書く。

## 1. 前提

### 1.1 開発機

| 項目 | 内容 |
|---|---|
| 機種 | Mac mini(Mac16,11、M4 Pro、メモリ 64 GB) |
| OS | macOS 27.2.1 |
| Xcode | 27.2(27B52) |
| ディスプレイ | Studio Display(5K、60 Hz)1 台だけ。内蔵ディスプレイはない |
| 署名 | Developer ID Application の証明書がキーチェーンにある |

この構成から、次の 3 点は開発機だけでは確かめられない。

- **内蔵ディスプレイでの 60 fps**(SPEC 3.11 の目標): 内蔵ディスプレイがないので、Studio Display の 5K・60 Hz で測る。SPEC の目標の書き方を、M0 の結果に合わせて直す。
- **120 Hz と、リフレッシュレートの違う画面の混在**: 120 Hz の画面がないので確かめられない。
- **複数ディスプレイ**(S1): 2 台目は、どうしても必要な場面に限って用意してもらう(7 章)。

EDR の余裕(`NSScreen` が返す値)は Studio Display でも 1 を超える可能性があるが、未確認である。S2 の最初に値を読む。

### 1.2 M0 で扱う範囲

M0 は【要検証】を消すための作業に限る。具体的には SPEC 8 章の S1〜S9 と、6.1 のログイン時の起動(`SMAppService`)である。後者は作者の了承を得て、SPEC 8 章に S10 として足した。

エフェクトの見た目の設計(雨と木漏れ日の重なり、3 Hz を超える輝度変動の測り方、描画の再現性)は M1・M2 で扱う。M0 で測るのは、その設計の前提になる合成の振る舞いまでとする。

### 1.3 API の確認

SPEC 10 章の 2 に従い、各スパイクの最初に、使う API の現行のシグネチャと対応 OS を公式ドキュメントで確かめる。計画づくりの途中で Codex は「`sharingType = .none` は画面の取り込みから除外する目的には使えない、と Apple が明記している」と指摘した。これはまだ確かめていない。S6 の最初に公式ドキュメントを読み、実測とあわせて判断する。指摘だけを根拠に SPEC から設定を消すことはしない。

## 2. 実験の置き場所と作り

```text
Spikes/
  Harness/        検証用の小さな AppKit アプリ(LSUIElement)。バンドル ID は 2 つ
  Fixture/        別プロセスで動く試験用の画面(格子、本文、重なるウインドウ)
  PackageProbe/   Metal のシェーダーを持つ SwiftPM パッケージと、描画の CLI(S9)
  scripts/        ビルド、署名、起動のスクリプト
docs/
  M0-PLAN.md      この文書
  SPIKES.md       結果
```

Fixture を別プロセスにするのは、オーバーレイが「他アプリの上」でどう合成されるかを確かめる必要があるからである。Harness と同じプロセスに試験用の画面を描くと、他アプリのウインドウとして扱われない。

スパイクのコードは使い捨てを基本にする。M1 に持ち込む候補は 5 章にまとめる。持ち込むときは M1 の設計に合わせて書き直し、Codex のレビューを通す。

### 2.1 権限の帰属

画面収録の許可(TCC)は、許可を求めたプロセスではなく、そのプロセスを起動した「責任のあるアプリ」に付くことがある。Claude Code から実行ファイルを直接起動すると、許可が Claude のデスクトップアプリに帰属し、結果を取り違えるおそれがある。そこで次のようにする。

- Harness は必ず .app にし、`open` で起動する。
- Developer ID で署名する。ad hoc の署名ではビルドのたびに署名の識別子(cdhash)が変わり、許可が外れる。
- 許可のある版とない版を、別のバンドル ID で分ける(仮に `…spike.granted` と `…spike.plain`)。
- `tccutil reset ScreenCapture <バンドル ID>` で、作者の手を借りずに未許可の状態へ戻せるかを最初に確かめる。戻せれば、許可を拒否した場合の試験を Claude が繰り返せる。

## 3. スパイク

各スパイクの「判定」は M0 で採否を決めるための目安である。数値の基準には【仮】を付けた。基準のないものは測って記録し、採否は作者と相談する。

### S9 パッケージ内の Metal シェーダー(先に行う)

- **確かめること**: SwiftPM のパッケージに置いた `.metal` が、採用するビルド手順でライブラリ(metallib)になり、アプリと CLI の両方から読み込めるか。
- **実験**: PackageProbe に `.metal` を 1 本置く。`Bundle.module` からライブラリを読み、4 ピクセルを描いて値を確かめる。`swift build`、`xcodebuild` の Release、書き出した .app の 3 通りで試す。
- **注意**: Xcode 27 の Metal ツールチェーンは、Mac を再起動するとマウント先が変わる(HanaLima で経験済み)。`metal` が見つからないというエラーは、`swift package clean` のあとに再試行してから判定する。
- **結果と仕様**: `swift build` で通れば、SwiftPM とスクリプトでビルドする(HanaLima と同じ形)。通らなければ、`xcodebuild` にそろえるか、ビルド時に `xcrun metal` で metallib を作って同梱する。採った手順を SPEC 3.2 と 3.12 に書く。
- **作者の操作**: なし。

### S3 無入力の時間と電源アサーション

- **確かめること**: 権限なしで最後の入力からの秒数を取れるか。動画の再生とビデオ会議を、他プロセスの電源アサーションで見分けられるか。画面のロック、スクリーンセーバー、ディスプレイのスリープを通知で知れるか(SPEC 2.2)。
- **実験**:
  1. `CGEventSource.secondsSinceLastEventType` を `.hidSystemState` と `.combinedSessionState` で比べる。キー、修飾キー、移動、クリック、ドラッグ、スクロールのそれぞれで値が 0 に戻るかを見る。
  2. オーバーレイを出したことで値が 0 に戻らないかを確かめる(S1 のあと)。ウインドウを出す操作が入力と見なされると、凪に入った直後に凪が終わる。
  3. `IOPMCopyAssertionsByProcess` で、`caffeinate -d` の開始と終了を検出できるか、`caffeinate -i` を誤って拾わないかを見る。続けて動画(Safari、QuickTime Player)とビデオ会議で、どの種類のアサーションが立つかを記録する。
  4. `NSWorkspace` などの通知で、ロック、スクリーンセーバー、ディスプレイのスリープとその復帰を受け取れるかを見る。
- **結果と仕様**: 取れた範囲で SPEC 2.2 と 3.8 を書く。動画や会議で取りこぼしがあれば、その旨を書き、一時停止の操作で補う。
- **作者の操作**: 入力の操作、動画の再生と停止、会議の開始と終了。1 は Claude が先に CLI で試せる。

### S1 オーバーレイ

- **確かめること**: 透明なオーバーレイが、すべての Space、他アプリのフルスクリーン、メニューバー、Dock の上に出て、クリックを下へ通すか。
- **実験**: Harness がディスプレイごとに枠なし・透明・影なしのウインドウを 1 枚出し、中身は不透明でない `CAMetalLayer` にする。ウインドウレベルと `collectionBehavior` の組を切り替えて、次を確かめる。
  - クリック、スクロール、ドラッグが下のアプリへ届く。メニューバーと Dock でも同じ
  - 出し入れしても、手前のアプリとキーウインドウが変わらない。ウインドウの切り替えの候補に出ない
  - 下のアプリのホバーとカーソルの形が乱れない
  - 別の Space、フルスクリーン、Stage Manager での見え方
  - ディスプレイの抜き差しと配置の変更のあと、位置とピクセル寸法が合い、古いウインドウが残らない(2 台目があれば)
  - `orderFront` から最初のフレームが見えるまでの時間
  - 凪でない間にウインドウを外したとき、描画の負荷が 0 になる
- **結果と仕様**: 通ったレベルとフラグの組を SPEC 3.7 に書く。フルスクリーンなどで安定しなければ、その状態では出さないと書く。フォーカスを奪う、クリックを止めるといった問題が残るなら、M1 に進まずに作者と相談する。
- **作者の操作**: Space、フルスクリーン、Dock、Stage Manager の操作と目視。2 台目のディスプレイがあれば抜き差し。

### S2 合成、階調、EDR

- **確かめること**: 乗算済みアルファの合成で、α ≈ 0・C > 0 の加算が他アプリの上で効くか。16 ビット浮動小数の出力とディザで、淡い影の縞が消えるか。EDR で紙の白より明るく出せるか(SPEC 3.5、4.1)。
- **実験**:
  1. Fixture に、暗・中・明の 3 つの背景と本文を出す。Harness がその上に試験用のパッチを重ねる。
  2. 合成の式の確認は数値で行う。画面収録を許可した Harness が、自分のオーバーレイを含めて画面を撮り(ScreenCaptureKit のスクリーンショット)、既知の背景との差から、減光、色かぶり、加算の効き方を求める。S4 の許可をもらったあとに行う。
  3. 縞は目視で判定する。撮った画像は表示の経路のディザを含まないので、数値では判定しない。0〜8 % の減光のランプを、8 ビットと 16 ビット浮動小数、ディザの有無の組み合わせで並べ、作者に見てもらう。
  4. EDR は、まず Studio Display での余裕(`NSScreen` の値)を読む。1 を超えれば、半透明のまま白より明るいパッチを出し、隣の白と比べて作者に見てもらう。1 のままなら、M1 の出力は SDR とし、EDR は対応ディスプレイを入手してから確かめると記録する。
- **結果と仕様**: 採った出力の形式と、加算の可否を SPEC 3.5 と 4.1 に書く。加算が効かなければ、ダークの外観での光の表し方を作者と相談する。
- **作者の操作**: 縞と EDR の目視。

### S5 権限なしのウインドウ情報

- **確かめること**: 画面収録の許可なしで、他アプリのウインドウの ID、矩形、前後の順序を取れるか(SPEC 3.10)。
- **実験**: 許可のない版の Harness で、`CGPreflightScreenCaptureAccess()` が false であることを確かめてから、`CGWindowListCopyWindowInfo` が返すキーを列挙する。Fixture のウインドウを 2 枚重ね、移動、リサイズ、前後の入れ替えをして、取れた値が画面と合うかを見る。15 Hz と 30 Hz で 1 回の取得にかかる時間を測る。タイトルとアプリ名は読まない。
- **結果と仕様**: 取れたキーと OS への依存を SPEC 3.10 に書く。矩形か順序が取れなければ、苔の生える場所を画面の隅だけにするか、苔を保留するかを作者と相談する。
- **作者の操作**: ほぼなし。ウインドウの操作は Fixture が自分で行う。

### S4 画面の取り込み

- **確かめること**: ScreenCaptureKit で自分のウインドウを除いて取り込めるか。IOSurface をコピーせずに Metal のテクスチャにできるか。取り込み中のメニューバーの表示、開始までの時間、遅れ、負荷(SPEC 3.9、5 章)。
- **実験**: `SCShareableContent` から自分のウインドウを除いた `SCContentFilter` を作り、`SCStream` を回す。フレームは `CVMetalTextureCache` でテクスチャにし、GPU の処理が終わるまで保持する。次を測る。
  - 自分のウインドウの除外: Harness が描いた目印が取り込みに写らないこと。ウインドウを作り直したあとも同じ
  - 凪入りから最初のフレームまでの時間(20 回)
  - Fixture の格子が変わってから、取り込んだフレームが届くまでの遅れ
  - CPU と GPU の負荷(GPU は `ioreg` の利用率で、sudo は使わない)
  - 停止したあと、フレームが届かなくなり、テクスチャが残らないこと
  - CPU へのピクセルの読み戻し、ファイルへの保存がないこと(コードで確かめる)
- **結果と仕様**: SPEC 3.9 の「1 フレームほど遅れる」を、測った条件と値に置き換える。開始が遅ければ、最初のフレームが届くまで雨を出さないと書く。インジケーターの出方を SPEC 5 章に書く。月 1 回の再確認の周期は短い試験では確かめられないので、確かめていないと記録する。
- **作者の操作**: 許可のダイアログ(拒否、許可、取り消し)、インジケーターの目視。

### S6 他アプリの画面共有とスクリーンショットへの写り込み

- **確かめること**: オーバーレイを、スクリーンショットと他アプリの画面共有から除けるか(SPEC 3.7、2.5)。
- **実験**: 最初に `NSWindow.sharingType` の公式ドキュメントを読む(1.3)。Harness の目印を `.readOnly` と `.none` で比べ、標準のスクリーンショット(全画面、範囲、ウインドウ)、ScreenCaptureKit を使う他アプリ、会議アプリの画面共有で写るかを見る。スクリーンショットのショートカットは入力なので、凪が終わってから撮られないよう、Harness は試験中だけ表示を保つ。
- **結果と仕様**: 除外できた経路とできなかった経路を記録する。除外を保証できなければ、SPEC 2.5 の「画面共有に写すかどうか」の設定と 3.7 の既定の書き方を、作者と相談して直す。
- **作者の操作**: スクリーンショットの操作と、会議アプリで共有した画面を相手側で見ること。S3 の会議と同じ時間にまとめる。

### S7 App Sandbox

- **確かめること**: App Sandbox の下で S3〜S5 と S10 が動くか(SPEC 6.1)。
- **実験**: 同じソースから、Sandbox あり・なしの Harness を作る。どちらも Developer ID と Hardened Runtime で署名し、実際に付いた entitlement を `codesign -d --entitlements` で確かめる。S3〜S5 と S10 を両方で繰り返す。
- **結果と仕様**: 全部通れば Sandbox を有効にする。必要な機能が Sandbox の下でだけ失敗するなら、Sandbox を外す案を作者に示す。
- **作者の操作**: Sandbox ありの版の画面収録の許可。

### S10 ログイン時の起動(追加を提案)

- **確かめること**: `SMAppService.mainApp` で登録、解除、状態の取得ができ、ログインのときに 1 回だけ起動するか(SPEC 6.1)。
- **実験**: Sandbox あり・なしの Harness を両方 `/Applications` に置き、両方を登録して再ログインし、両方を解除してもう一度再ログインする。両方を同時に試すので、再ログインは 2 回で済み、失敗が Sandbox によるものかを見分けられる。S7 の採否はこの結果を見てから決める。システム設定で無効にした状態が `status` に表れるかも見る。
- **結果と仕様**: 状態の扱いを SPEC 6.1 に書く。承認待ちの状態があれば、システム設定へ案内する画面を M1 に入れる。
- **作者の操作**: 再ログイン 2 回とシステム設定の操作。最後に登録を解除する。

### S8 NSGlassEffectView(任意)

- **確かめること**: 画面収録の許可なしに、雨粒の屈折の代わりになるか。
- **実験**: Harness に `NSGlassEffectView` を数個置き、形と大きさを変えて、下の文字がどう歪むかを見る。1 時間で区切る。
- **結果と仕様**: 形や歪みを制御できず、非アクティブなウインドウで曇るなら不採用と記録する。行うかどうかは作者に確かめる(7 章)。
- **作者の操作**: 目視。

### macOS 26 の扱い

作者の判断で、確かめるのは 27.2.1 だけとする(7 章)。採った経路はデプロイメントターゲットを 26 にしてビルドし、SDK の対応 OS の表示だけを確かめる。SPIKES.md には「27.2.1 でのみ確認」と書き、最低 OS(SPEC 9 章の未決事項)の判断は作者に残す。

## 5. 記録の書式と M1 への持ち込み

`docs/SPIKES.md` の冒頭に、`ID | SPEC の節 | 判定 | 採った案` の一覧を置く。各スパイクは次の書式で書く。

```markdown
### Sx 確かめること
- 判定: 合格/条件付きで合格/不合格/未実施
- 環境: OS のビルド、SDK、ディスプレイ(倍率、Hz、EDR の余裕)、署名、Sandbox、権限の状態
- 手順: ビルドと起動のコマンド、作者の操作、比べたもの
- 結果: 試行の回数、測った値、目視の結果
- 仕様への反映: SPEC の節と、直した内容。縮退の条件
- M1 への持ち込み: 移すコードと移す先
```

画像や動画は残さない。画面を撮った画像は解析が済んだら消し、数値だけを残す。取り込んだ画面をディスクに書かないという SPEC 5 章の約束は、検証の段階でも守る。

M1 に持ち込む候補は、オーバーレイのウインドウの作り方と画面の座標の変換(S1)、出力の色空間と形式(S2)、無入力の判定と起きる時刻の計算(S3)、シェーダーの置き方とビルドの手順(S9)、ログイン項目の状態の扱い(S10)。S4 のテクスチャの寿命の管理は M2 に、S5 の矩形と順序の変換は M3 に持ち込む候補とする。

M0 は、SPEC のすべての【要検証】に、測った結果か採る縮退の仕様が対応し、作者が SPEC の修正を確認したときに終える。

## 6. 2 つの案の突き合わせ

| 点 | 採った案 | 理由 |
|---|---|---|
| S10(ログイン時の起動)を独立させる | Codex | Claude の案は S7 に含めていたが、再ログインという作者の操作が要り、手順も別なので分けたほうが管理しやすい |
| Fixture を別プロセスにする | Codex | 合成は他アプリのウインドウの上で確かめる必要がある |
| 立ち会いを許可なし・許可・ログインの 3 回に分ける | Codex | Claude の案は 1 回にまとめていたが、許可の前にしか試せない項目がある |
